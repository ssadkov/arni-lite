# Arni Lite для Windows: спецификация и проблемы реализации

Дата: 10 ноября 2026 года. Версия документа: 1.1.

Изменения 1.1 после ревью: ядро в `netstandard2.0` (задел под Linux, сам Linux вне MVP); Markdown-рендер перенесён в P1; вход Yandex + Google через мост поверх существующего веб-входа; уточнены TLS, prerequisites Win7, запуск PowerShell, остановка дерева процессов и оценка сроков. Основание: есть несколько оплаченных заявок от пользователей старых Windows.

Статус: проект спецификации для независимого ревью и последующей реализации. Приложение ещё не создано; запуск на старых Windows и показатели производительности не проверены. Предложенные API явно отделены от существующих.

## 1. Задача и рекомендуемое решение

Создать отдельный лёгкий Windows-клиент Arni с полноценным диалогом с ИИ, работой с файлами выбранного проекта и выполнением обычных команд на компьютере пользователя.

Целевые системы: Windows 7 SP1 и Windows Server 2012 Standard с графическим рабочим столом, а также современные Windows 10/11 на x64. На пользовательском скриншоте именно Windows Server 2012, а не «Windows 12» и не обязательно Server 2012 R2.

Рекомендуемая основа: C# + WPF + **.NET Framework 4.8, target framework `net48`**. Компонент редактирования текста — AvalonEdit с совместимым `net462`-артефактом. UI чата — нативные WPF-контролы; в MVP ответ показывается обычным текстом с моноширинными блоками кода и кнопкой копирования, полноценный Markdown — P1. Логика без UI (`Core`, `Api`, `Storage`) собирается как `netstandard2.0` и не ссылается на WPF/Win32, чтобы позже её можно было переиспользовать под Linux. Electron, Chromium, WebView2, VS Code, современный Node.js и Copilot SDK не входят в обязательные зависимости.

Выбор WPF — инженерное предложение, а не уже утверждённое результатами прототипа решение. Подтвердить его на этапе G0. Не подменять .NET Framework 4.8 современным .NET 8/10 или обязательным Framework 4.8.1: это другой набор требований к ОС.

Первая версия должна решать пользовательские задачи, а не воспроизводить все возможности ArniCode/VS Code. Если обычным пользователям достаточно чата и команд, редактор остаётся компактным вспомогательным инструментом.

## 3. Объём первой версии

### 3.1. Обязательные функции MVP

1. Вход в существующий аккаунт Arni через внешний браузер провайдерами Yandex и Google (раздел 8.3); выход и повторный вход.
2. Получение доступных конкретному аккаунту моделей и состояния бюджета с backend.
3. Чат с потоковым ответом, историей, новым диалогом, отменой и понятными ошибками. Ответ — обычный текст; блоки кода между тройными обратными кавычками выделяются моноширинным шрифтом и копируются одной кнопкой. Остальная Markdown-разметка в MVP показывается как есть.
4. Режим «Чат» без локальных инструментов и режим «Агент» с выбранным проектом.
5. Выбор одной локальной папки проекта на диалог.
6. Просмотр файлов, чтение текста, создание и изменение текстовых файлов с предварительным просмотром изменений.
7. Запуск неинтерактивных команд через `cmd.exe` и доступный Windows PowerShell, получение stdout/stderr и exit code.
8. Последовательный цикл: модель → вызов инструмента → локальное действие → результат → модель.
9. Подтверждение запуска команд и применения изменений; отдельная настройка доверия к выбранному проекту.
10. Локальное сохранение истории и восстановление незавершённого состояния после перезапуска.
11. Диагностика совместимости: ОС, Framework, TLS, браузер, shell, доступ к API.
12. Portable ZIP и установка в профиль пользователя, сосуществующие с текущим ArniCode.

### 3.2. Следующий этап, P1

- Полноценный Markdown в чате: заголовки, списки, таблицы, ссылки, подсветка кода.
- Скриншоты/PNG/JPEG в чате для моделей с vision.
- Фоновая команда с ограниченным журналом и явной кнопкой остановки.
- Расширенный diff, поиск по проекту с исключениями, удобные массовые изменения.
- Открытие результата в ассоциированной программе после действия пользователя.
- Дополнительные способы входа, x86-пакет при подтверждённом спросе.
- Подписанное автоматическое обновление после испытаний ручного обновления.

### 3.3. За пределами MVP

- Совместимость с расширениями VS Code, перенос workbench и Copilot SDK.
- Отладчик, LSP для всех языков, встроенный Git-клиент уровня IDE.
- Полноценный интерактивный терминал: TUI, readline, пароли через терминал, псевдотерминал.
- Автоматическое управление браузером/рабочим столом, MCP-серверы и плагины сторонних разработчиков.
- Автоматическая установка Python, Node, Git, FFmpeg и другого окружения.
- Редактирование содержимого DOCX/XLSX/PDF как обычного текста. Для таких задач нужны отдельные инструменты и совместимые внешние программы.
- Server Core, служба без интерактивного сеанса, macOS, native ARM64, Windows XP/Vista.
- Linux-клиент. В MVP делается только задел: ядро в `netstandard2.0` без WPF/Win32 (раздел 5.1). Условие пересмотра — подтверждённые заявки с Linux; тогда сначала сравнить с Linux-сборкой текущего ArniCode, которая на современном Linux может оказаться дешевле отдельного UI.

Смена интерфейса не обеспечит запуск современных сторонних программ, если сами они не поддерживают старую ОС.

## 4. Платформенная матрица

| ОС/архитектура | Требование |
| --- | --- |
| Windows 7 SP1 x64 | Обязательно; документированный минимальный набор обновлений, Framework 4.8 и рабочий HTTPS |
| Windows Server 2012 Standard x64, Desktop Experience/обычный GUI | Обязательно; отдельно от 2012 R2, в том числе RDP-сеанс |
| Windows 10 x64 | Обязательно на выбранном современном образе с Framework 4.8+ |
| Windows 11 x64 | Обязательно на актуальном на дату релиза образе, включая Framework 4.8.1 |
| Windows 7 SP1 x86 | P1; отдельная упаковка и испытания, не обещать через x64-пакет |
| Windows Server 2012 R2 / Server 2016+ | Дополнительная проверка; не считать автоматически пройденной |
| Windows 11 ARM64 | P2; не обещать работу через эмуляцию без проверки зависимостей |

Поддержка здесь означает совместимость приложения, а не наличие поддержки ОС со стороны Microsoft. Не обещать совместимость с любой будущей версией Windows.

Базовый x64-пакет должен быть одинаковым для четырёх обязательных ОС. Если потребуется раздельная версия библиотек или установщика, явно задокументировать причину.

### 4.1. Окружение пользователя

- Для сетевого ИИ нужен интернет; локальная модель не требуется.
- Ориентир для испытаний: 2 ядра, 2–4 ГБ RAM; пользовательский i7-3630QM/8 ГБ — дополнительный реальный сценарий, а не измеренный стенд.
- Базовое разрешение 1280×720, работа при 100/125/150/200% DPI; клавиатурная навигация.
- WPF должен работать без обязательного современного GPU, включая программный рендеринг и RDP.
- Framework устанавливается отдельно, если отсутствует. Portable не означает отсутствие Framework или системных prerequisites.
- Приложение запускается с обычными правами. Установка Framework может требовать администратора и перезагрузки; не устанавливать его незаметно.
- Ожидаемый минимальный образ Win7: SP1 + KB4474419 и KB4490628 (поддержка SHA-2, без неё не запускается сам установщик Framework 4.8 и не проверяются подписи) + KB4019990 (D3DCompiler для WPF). Список взят из документации и подлежит подтверждению на чистом образе в G0; итоговый перечень KB/корневых сертификатов фиксируется по результатам испытаний. Не править системные TLS-настройки молча.

## 5. Архитектура

```text
WPF UI: чат / файлы / редактор / вывод команд
                  |
          Application services
                  |
       AgentOrchestrator / ChatService
         |          |           |
    Arni API     ToolRegistry   LocalStore
         |          |
  существующий   WorkspaceService + ProcessRunner
     backend       |                 |
         |       файлы        cmd / Windows PowerShell
       модели
```

Модель работает на стороне существующего inference/backend. Файлы читаются и команды выполняются на компьютере пользователя. Локальный агент отправляет модели только выбранный контекст и результаты инструментов.

### 5.1. Предлагаемая структура отдельного проекта

```text
ArniLite.sln
src/
  ArniLite.App/             # net48, WPF, MVVM, composition root
  ArniLite.Core/            # netstandard2.0, модели, оркестратор, политики
  ArniLite.Api/             # netstandard2.0, HttpClient, DTO, SSE, auth
  ArniLite.Windows/         # net48, процессы, DPAPI, Win32 interop
  ArniLite.Storage/         # netstandard2.0, журнал диалогов, настройки
tests/
  ArniLite.UnitTests/
  ArniLite.IntegrationTests/
  ArniLite.CompatibilityTests/
packaging/
docs/
```

Это ориентир; число проектов можно сократить, сохранив границы ответственности. Обязательная граница одна: `Core`, `Api` и `Storage` не ссылаются на WPF, `System.Windows.*`, реестр, DPAPI и P/Invoke. Запуск процессов, хранилище токена, определение ОС и shell они получают через интерфейсы, реализованные в `ArniLite.Windows`. Это задел под будущий Linux-клиент, а не обещание его сделать; `netstandard2.0` не отменяет раздел 6.1 — API, отсутствующие во Framework 4.8, по-прежнему недоступны. Создание отдельного репозитория предпочтительно изменению ядра текущего VS Code. Если начало идёт в существующем checkout, использовать явно отдельный каталог и не менять текущий production-клиент ради прототипа.

## 6. Зависимости и сборка

1. Компилировать приложение под `net48`; сборочная машина может быть современной Windows с MSBuild/SDK и reference assemblies для Framework 4.8.
2. Зафиксировать версии всех NuGet-пакетов. Проверять именно runtime-совместимость выбранного артефакта, а не наличие пакета в NuGet.
3. AvalonEdit — совместимая сборка `net462`. Не подтянуть случайно вариант только для современного .NET.
4. JSON — библиотека с подтверждённой поддержкой net48; предпочтительно Newtonsoft.Json. Конкретную версию зафиксировать после проверки.
5. Markdown в MVP не рендерится: обычный текст плюс выделение блоков кода (раздел 3.1, п. 3). Сообщение хранить как исходный текст модели, чтобы P1-рендерер можно было добавить без миграции истории. В P1 — нативный WPF-рендерер с совместимыми зависимостями, не WebView2.
6. История MVP — локальные версионированные JSON/JSONL-файлы с append-журналом, безопасной записью метаданных и восстановлением усечённой последней записи. SQLite возможен позже после выбора совместимого native-пакета.
7. Не переносить `node:sqlite`, `undici`, `node-pty`, современный Node, Python или браузерный runtime как обязательную зависимость.
8. Собрать SBOM/список лицензий и dependencies, приложить их к пакету. Не переносить vendor assets/branding сторонних сервисов автоматически.
9. Добавить application manifest с корректными supported OS declarations и `asInvoker`. Проверять фактическую версию ОС, не полагаться на виртуализованный `GetVersionEx` без manifest: неправильное определение системы даст модели неверные capabilities.
10. Настройки DPI и P/Invoke должны иметь fallback для Win7: новые Win32-функции загружать условно, отсутствие API не должно ломать загрузку всего процесса.

### 6.1. API, которых нет в обычном net48

Особое внимание: `ProcessStartInfo.ArgumentList`, `Process.WaitForExitAsync`, `Process.Kill(entireProcessTree: true)`, современные overloads потоков с CancellationToken, `File.Move(..., overwrite: true)` и некоторые методы Path/Encoding. Их наличие в свежем C# примере не означает наличие во Framework 4.8.

Писать совместимые адаптеры и Win32 interop. Современный компилятор не добавляет отсутствующие runtime API. Проверять и транзитивные зависимости, binding redirects, P/Invoke и минимальную ОС native DLL.

## 7. Пользовательские сценарии и интерфейс

### 7.1. Первый запуск

1. Показать окно без ожидания ответа сети.
2. Выполнить диагностику в фоне; при невозможности работы показать конкретную причину и способ исправления.
3. Предложить вход во внешнем браузере. Не встраивать страницу OAuth в Internet Explorer/WPF WebBrowser.
4. После входа показать аккаунт, модели и бюджет. Ошибка каталога не должна стирать локальную историю.
5. Чат работает без проекта. При переходе в «Агент» пользователь выбирает папку и видит описание локальных возможностей.

### 7.2. Основной экран

- Слева — диалоги; дерево проекта показывается при необходимости.
- В центре — чат обычным текстом с выделенными блоками кода, копированием текста/кода и карточками инструментов.
- Редактор/diff открывается вкладкой или дополнительной панелью.
- Внизу — ввод, выбор режима/модели, отправка/остановка.
- Вывод команды — сворачиваемая карточка с состоянием, временем, exit code, stdout/stderr и остановкой.
- Постоянно различимы выбранный проект, модель и состояние запроса.
- Русский интерфейс MVP; все строки готовы к локализации.

### 7.3. Диалог

- Сохранять полный диалог, а не только последнее сообщение.
- Текстовый ответ доступен по мере поступления; копирование не ждёт завершения.
- Новый диалог получает новый ID и отдельную историю расходов.
- Нельзя менять модель, проект или отправлять следующий user turn в середине активного цикла. Сначала завершить/остановить текущий.
- В MVP один активный агентный turn во всём приложении. Остальные диалоги можно просматривать; явная очередь/параллельность — позже.
- Учитывать несколько экземпляров приложения: single-instance coordination для одного Windows-пользователя и явные locks/revisions для project changes. Однопоточный UI не защищает от второго процесса.
- Отмена фиксируется как отдельное состояние, частичный текст сохраняется.
- Отмена клиентом не гарантирует отсутствие списания: backend может дочитывать оплаченный upstream для учёта usage.

### 7.4. Контекст и файлы

- Пользователь видит, какие файлы/фрагменты отправляются модели.
- Не индексировать и не отправлять весь диск/проект автоматически.
- По умолчанию исключить `.git`, зависимости, build outputs, секреты, `.env`, приватные ключи, большие бинарные файлы. Точное правило и явные исключения пользователя документировать.
- Применять бюджет контекста из каталога модели; большие результаты сокращать с явной отметкой.
- При переполнении предлагать новый диалог или явное сжатие. Не терять связи tool call/result и незавершённые действия.
- Компактация истории сама может быть платным запросом; это должно быть видно пользователю.

### 8.2. Streaming

- `HttpClient` с `ResponseHeadersRead`; не ждать загрузки всего response body.
- Читать UTF-8 инкрементально: символ может быть разделён между network chunks.
- Корректно обрабатывать LF/CRLF, несколько `data:`-строк, комментарии/keepalive и пустую строку как разделитель события.
- JSON-пакет SSE может быть разбит на любое число chunks; несколько событий могут прийти вместе.
- Собирать tool calls по индексу, ID и fragment arguments. Имя/ID могут присутствовать только в первой delta; индексы не обязаны быть последовательными.
- Выполнение инструмента допустимо только после полностью собранного и проверенного ответа модели. Частичный JSON команды не выполнять.
- Отличать `finish_reason=tool_calls`, `stop`, `length`, usage-only chunks, `[DONE]`, error и транспортный EOF.
- Если конец потока не подтверждён по согласованному контракту, turn считается прерванным. Нельзя угадывать недостающие arguments.
- При `length` не выполнять незавершённые tool calls; показать достижение лимита.
- Обязателен non-stream fallback через тот же endpoint для диагностики; отсутствие streaming не должно навсегда лишать пользователя простого чата.
- Старый parser в `extensions/arni-agent/src/providers/arniProvider.ts` нельзя копировать как эталон: он делит каждый chunk по строкам и игнорирует ошибки незавершённого JSON, что может терять данные на границе chunks.

### 8.3. Авторизация: решение до G1

Не хранить пароль пользователя и не встраивать confidential OAuth client secrets. JWT backend и тем более signing secret не генерируются на клиенте.

**Выбранный путь: мост поверх существующего веб-входа.** OAuth в клиенте Lite не реализуется. Пользователь входит в браузере на сайте Arni тем же серверным кодом, что и веб-чат (Google, Yandex, VK уже есть в `src/app/api/web/auth/`), а Lite получает Arni JWT опросом. Так клиент сразу получает все провайдеры, включая будущие, и не содержит ни client secret, ни provider-специфичной логики. Обязательные для MVP провайдеры — Yandex и Google.

Предлагаемые ниже endpoints и страница **ещё не реализованы**; это небольшая работа на backend и веб-фронтенде, которую нужно сделать до G1. Не писать клиент так, будто они уже есть:

1. `POST /api/desktop/auth/start` возвращает высокоэнтропийный `device_code` (секрет клиента), публичный `request_id`, короткий `user_code` для сверки глазами, `verification_uri`, `expires_in` и интервал polling.
2. Клиент открывает `verification_uri` — HTTPS-страницу сайта Arni с `request_id`. Если пользователь не вошёл, страница ведёт его через существующие `/api/web/auth/<provider>/start` → `callback` → login code → `/api/web/auth/session`. `request_id` должен пережить редирект к провайдеру и обратно; способ (параметр, cookie или storage страницы) выбрать при реализации, не ослабляя проверку `state`.
3. Вошедший пользователь видит название приложения и `user_code` и явно подтверждает привязку: страница вызывает новый `POST /api/desktop/auth/approve` с `request_id` и своим Bearer JWT.
4. `POST /api/desktop/auth/token` с `device_code` возвращает pending/slow_down/denied/expired либо Arni JWT для подтвердившего аккаунта.
5. Сервер хранит challenge с TTL, ограничивает частоту запросов, атомарно связывает его с аккаунтом. Получение токена защищено секретом, известным только клиенту. Ни `request_id`, ни короткий пользовательский код сами по себе не дают скачать JWT.
6. Запретить произвольный redirect/open redirect и передачу JWT или `device_code` в URL. Логи не содержат challenge secrets, JWT и access-bearing URLs.
7. Описать потерю ответа при выдаче токена: повтор должен быть безопасным либо требовать нового login flow; не оставлять неограниченно повторяемый exchange.

Отклонённая альтернатива: Yandex OAuth Authorization Code + PKCE в самом клиенте через loopback и существующий `/api/auth/exchange`. Она даёт только Yandex (в исследованном `/api/auth/exchange` есть ветки Yandex и VK, Google-ветки нет) и требует отдельной регистрации приложения у каждого провайдера. Возвращаться к ней только если мост окажется невозможен.

G0 записывает ADR по мосту и проверяет на Win7 и Server 2012: (а) страницы входа Yandex и Google открываются и проходят в Firefox 115 ESR; (б) ключи Google настроены в production (`/api/web/auth/google/start` отвечает 503, если нет); (в) что видит пользователь, у которого браузер по умолчанию — Internet Explorer: вход там не обязан работать, но обязательна кнопка «Скопировать ссылку» и понятная подсказка открыть её в другом браузере.

Токен хранить через Windows DPAPI `CurrentUser` вне project/history. Выход удаляет локальный токен и разрешения. Локальный logout не равен серверному отзыву всех JWT. Исследованный `src/lib/jwt.ts` выдаёт JWT на 30 дней; штатный refresh/revoke контракт не подтверждён. При истечении нужен повторный вход, если новый контракт не добавлен.

### 8.4. Модели, бюджет и ошибки

- Не hardcode ID, цены, бесплатность и права пользователя.
- `GET /api/models` возвращает `data`, account-specific metadata и provider/capability сведения; хранить совместимые DTO, допускающие новые поля.
- Не все модели одинаково поддерживают tools/vision; неизвестную capability проверять и не обещать. Отказ tools не переключать молча на другую платную модель.
- Тарифы/лимиты и списание остаются серверными. Клиент не повышает квоты и не объявляет запрос бесплатным по собственной оценке.
- Деньги хранить в integer micro-USD или decimal, не binary float. Конверсия RUB/KZT — отображение по серверным rates; при отсутствии курса показывать USD. Не подменять фактический ledger локальной оценкой.
- Каждый model request внутри одного агентного turn может тарифицироваться отдельно. Показывать прогресс, число шагов и доступную серверную статистику.
- Связывать все model calls диалога через постоянный `X-Arni-Chat-Id`. Локальный turn ID и tool call ID — отдельные сущности.
- `401`: остановить цикл, предложить вход. `403`: доступ/аккаунт/модель. `402`: бюджет/тариф. `429`: лимит и Retry-After. `400`: контекст/параметры. `5xx`: ошибка сервиса.
- Согласовать normalizer: backend использует как строковый `error`, так и объект с `code/message`. Не показывать пустую ошибку из-за отличия DTO.
- POST inference после обрыва не повторять автоматически: списание/обработка могли уже произойти. GET допускает ограниченные повторы; ручной повтор inference явно отмечать как новый запрос.

## 9. Локальные инструменты и цикл агента

### 9.1. Инструменты версии 1

| Имя | Аргументы | Поведение |
| --- | --- | --- |
| `list_files` | relative `path`, optional depth/limit | Ограниченный список с исключениями; без бесконечной рекурсии |
| `read_file` | relative `path`, start_line, max_lines | Текст, encoding, line endings, hash/revision; лимит вывода |
| `search_text` | query, optional path/glob, limit | Буквальный поиск MVP; regex только с timeout и лимитами |
| `propose_file_change` | path, expected_hash либо must_not_exist, content | Создать preview, ничего не записывать до согласия |
| `run_command` | shell, command, relative cwd, timeout_ms | Запуск ограниченной по времени неинтерактивной команды после согласия |

После одобрения change клиент применяет его и возвращает результат того же tool call. Отдельный `apply_change`, доступный модели без участия UI, не нужен. Multi-file atomic transaction в MVP не обещается; результат фиксируется по каждому файлу.

Удаление файлов, выполнение произвольного EXE вне разрешённых shell, HTTP fetch, открытие URL моделью, registry и elevation не входят в tools v1. Shell технически может выполнить многие из этих действий; это отдельная граница доверия, см. раздел 11.

### 9.2. Результат инструмента

```json
{
  "schema_version": 1,
  "tool_call_id": "call_example",
  "status": "completed",
  "result": {
    "exit_code": 0,
    "stdout": "Проверка пройдена",
    "stderr": "",
    "duration_ms": 320,
    "truncated": false
  }
}
```

Варианты status: `completed`, `denied`, `cancelled`, `timed_out`, `failed`, `outcome_unknown`. Для файлов результат имеет другие поля, включая hash и affected paths. Ошибка инструмента возвращается модели как результат, а не приводит к молчаливой потере tool call.

В model history записать исходный assistant message с `tool_calls` и соответствующее `role: tool`, `tool_call_id`, `content` как JSON-строку. Не добавлять UI metadata в поля, не поддерживаемые backend.

### 9.3. Машина состояний

```text
Idle → RequestingModel → ReceivingModel
    → ValidatingTools → AwaitingPermission → ExecutingTool
    → PersistingToolResult → RequestingModel … → Completed

Из активного состояния: Cancelling → Cancelled
Ошибка: Failed / OutcomeUnknown / AwaitingLogin / BudgetBlocked
```

- Выполнять tools последовательно в MVP, включая несколько calls в одном ответе. Сохранять ID/order и выдавать результат каждому call.
- Не продолжать mutation chain после отклонённого/неопределённого действия автоматически. Дать модели корректный denial/error и ограниченный шанс завершить ответ без повторного навязывания действия.
- Предложенные defaults: максимум 12 model rounds, 30 tool calls, 15 минут на turn, одна команда одновременно. Лимиты настраиваемые и видимые, не равны серверным бюджетам.
- Повторяющиеся одинаковые вызовы/ошибки останавливать с объяснением. Контекст tool output ограничен.
- Отмена блокирует запуск последующих calls, отменяет HTTP, останавливает принадлежащие приложению команды и сохраняет состояние.
- Ни текст Markdown, ни строка «выполни команду» в обычном ответе не являются структурированным tool call.

### 9.4. Защита от повторного действия

До side effect сохранить локальный journal record: chat/turn/call ID, arguments hash, состояние `prepared`, затем `executing`, затем terminal result. Ключ дедупликации включает turn + model-round + tool-call ID; дополнительно хранится hash аргументов.

После падения при `executing` результат может быть неизвестен. Не запускать ту же команду автоматически при восстановлении. Показать неопределённость и предложить сначала проверить состояние. При восстановлении истории неизвестному call соответствует явный error/outcome_unknown; не отправлять модели фиктивный success.

Это локальная защита от replay. Она не обеспечивает exactly-once выполнение произвольной команды и не заменяет серверную идемпотентность inference/биллинга.

## 10. Файлы и текстовый редактор

- Одна папка проекта, относительные пути. `cwd` не меняет корень проекта молча.
- Проверять абсолютный нормализованный путь и принадлежность корню с учётом separator boundary и case-insensitive Windows comparison.
- Обрабатывать `..`, absolute paths, UNC, device paths, alternate data streams, symlinks/junctions/reparse points, зарезервированные имена. В MVP отклонять reparse point traversal и UNC-проекты с понятной ошибкой.
- Проверять реальную цель открытия/записи; одной строковой проверки prefix недостаточно. Ограничить race между preview/check и записью; изменение цели/версии делает proposal устаревшим.
- При работе в редакторе у unsaved buffer есть своя revision. Агент не должен перезаписать несохранённый текст или изменения другой программы.
- Перед записью сверить `expected_hash`/revision. При конфликте заново показать diff, не подставлять новый hash без согласия.
- Запись через временный файл в той же папке и подходящий механизм замены; не удалить оригинал до надёжной записи. Сохранять backup и метаданные кодировки.
- В MVP rollback только для изменений приложения, если после них файл не менялся. Не обещать откат команд и всех внешних изменений.
- Сохранять UTF-8 BOM/no BOM, UTF-16, CP1251 и CRLF/LF по исходному файлу. Не угадывать неоднозначную кодировку молча; дать выбор. Новые текстовые файлы — UTF-8, стандарт проекта для line endings.
- Предложенные limits: read_file до 500 строк/64 КиБ на результат; обычный editable file до 5 МиБ; pagination для больших текстов. Binary не открывать как текст.
- Базовый редактор: вкладки, номера строк, undo/redo, поиск, подсветка популярных языков, dirty indicator, сохранение и просмотр diff.
- Большие деревья файлов загружать лениво. Поиск/перечисление имеют cancellation, limits, игнорируют .git и dependencies.
- Long paths на Win7 и части Framework API имеют ограничения. В MVP поддержать обычные пути и заранее диагностировать слишком длинные; не обещать универсальный обход через `\\?\`. Проверять ACL/access denied, locked files и сетевые отключения без потери оригинала.

## 11. Команды, права и ограничения

### 11.1. Запуск процесса

- Shell v1: `cmd.exe` и системный `powershell.exe`; `pwsh.exe` только если обнаружен и выбран пользователем.
- Версию Windows PowerShell определять: на Win7 может быть 2.0, на Server 2012 — 3.0; не предполагать 5.1/7.0. Передавать реальные capabilities модели.
- Для PowerShell основной кандидат — `-NoProfile -NonInteractive -Command -` с передачей текста команды через stdin. `-EncodedCommand` из неизвестного exe — типовая сигнатура вредоносного ПО и может вызывать срабатывания Defender/Касперского; оставить его запасным вариантом. `-File` с временным скриптом упирается в ExecutionPolicy, которая на клиентских Windows по умолчанию Restricted; не применять `ExecutionPolicy Bypass` по умолчанию. В G0 проверить выбранный способ на PowerShell 2.0/3.0/5.1: кириллицу, multiline, exit code и реакцию антивируса.
- Для cmd использовать документированную стратегию `cmd /D /S /C`, quoting и при необходимости временный script. Тестировать пробелы, кавычки, `%`, `!`, `&`, `^`, кириллицу и multiline. Не собирать команды строковой подстановкой путей без shell-escaping.
- Structured program launch при необходимости — отдельный внутренний API. В net48 нет удобного `ArgumentList`: правила quoting должны быть явными.
- `UseShellExecute=false`, без elevation, с потоковым чтением stdout и stderr одновременно; не вызывать последовательный `ReadToEnd`, который может дать deadlock.
- Закрывать stdin для неинтерактивных задач. Программы, требующие ввода, завершаются с понятной диагностикой/timeout; не зависать навсегда.
- Зафиксировать cwd и нужные переменные окружения. Токен Arni и внутренние secrets не передавать дочернему процессу автоматически.
- Кодировки выводов различаются: OEM/CP866, ANSI/CP1251, UTF-8 и PowerShell имеют разные правила. Определить policy, тестировать incremental decoding и позволить override.
- Объединённый вывод не гарантирует точный порядок строк разных потоков; хранить stream+sequence/timestamp и не утверждать более строгий порядок.
- Предложенные defaults: timeout 120 секунд, верхняя граница 600 секунд, model-visible output 64 КиБ, UI ring buffer 2 МиБ. Truncation видима. Полный disk log ограничен квотой; переполнение не блокирует drain stdout/stderr.
- Модель получает реальные exit code/status. Нулевой exit code не подменяет проверку результата; PowerShell non-terminating errors также учитывать.

### 11.2. Отмена дерева процессов

`Process.Kill()` во Framework 4.8 не равен остановке всего дерева. Предпочтительно Win32 Job Objects с kill-on-close и корректной привязкой дочернего процесса до выполнения пользовательского кода, например suspended create → assign → resume.

На Windows 7 нет nested jobs; запуск приложения под внешним Job Object может мешать assignment. На Server 2012 nested jobs появились, но это отдельный сценарий. Проверить обычный запуск, launcher и RDP. Если привязка к Job Object невозможна, команды не отключать: использовать запасной путь — снимок дерева по parent PID и завершение процессов по одному. Этот путь менее надёжен (процесс может успеть породить потомка или сменить родителя), поэтому в таком режиме показывать пользователю, что «Стоп» может оставить дочерние процессы, и после остановки перечислять уцелевшие. Не рекламировать «Стоп» как надёжный при оставшихся детях.

Job Object — механизм управления процессами, не полная security sandbox. Возможны escapes через внешние службы/планировщик и независимые процессы; MVP не обещает сдерживание враждебного кода.

### 11.3. Согласие и граница доступа

- По умолчанию read-only tools работают после явного выбора проекта. Запись требует preview, shell — показа команды и cwd перед выполнением.
- Отказ возвращается модели как denial. Нельзя заменить отказанный tool вызовом другого инструмента с тем же side effect.
- Допустима опция «разрешить действия в этом проекте до конца сеанса» с понятным объяснением. Не включать её автоматически; не переносить доверие на другой корень/аккаунт.
- **Произвольная shell-команда имеет права пользователя на весь доступный ему компьютер. Выбранная папка и cwd не являются песочницей.** В UI не обещать обратное.
- Не подменять разрешения regex-блоклистом «опасных команд»; это лишь вспомогательный сигнал, а не защита.
- Приложение и агент не запрашивают UAC автоматически. Действие с повышенными правами пользователь выполняет отдельно.
- Содержимое файлов, вывод команд и тексты из сети — данные, а не новые разрешения. Они не изменяют policy и не дают доступ к токену приложения.

## 12. Сеть, вход и особенности старой Windows

1. Framework использует Windows Schannel. Работа HTTPS зависит от ОС, cipher suites, TLS 1.2, времени и цепочки доверия. Проверить handshake именно с фактическими API/auth/update хостами.
2. На Win7 и Server 2012 системный default для .NET — не TLS 1.2, поэтому «системный выбор» там даст отказ соединения. Приложение при старте на ОС старше Windows 10 явно задаёт TLS 1.2 для своего процесса (`ServicePointManager.SecurityProtocol`); на Windows 10/11 оставляет системный default, чтобы не отрезать TLS 1.3 (значение `SystemDefault` равно нулю, поэтому `|= Tls12` на новой ОС оставило бы только TLS 1.2). Это настройка процесса, системный реестр не трогать. Не понижать соединение до TLS 1.0/1.1.
3. Нельзя исправлять ошибку сертификата через accept-all validation callback. Выдавать диагностическую ошибку и инструкции. Цепочка `api.arnion.ru` идёт до ISRG Root X1: на изолированном Server 2012 без автообновления корневых сертификатов его может не быть. Диагностика должна отличать «нет корня» от прочих ошибок TLS и давать инструкцию по установке корня средствами Windows.
3a. По пробе 10.11.2026 единственный общий с Win7 шифр на `api.arnion.ru` — `ECDHE-RSA-AES128-SHA` (сертификат RSA, а ECDHE-RSA-GCM в Schannel Win7 нет). Требование к серверу: записать в конфигурацию nginx, что этот шифр нужен для Arni Lite, и добавить проверку в мониторинг/деплой — «ужесточение TLS» молча отключит всех пользователей Win7. Более прочный вариант на будущее — второй, ECDSA-сертификат: с ним Win7 получит AES-GCM.
4. Если сервер/CDN перестанет принимать доступные Win7 TLS/ciphers, понадобится изменение сетевого решения или отдельно поддерживаемая TLS-библиотека. Это реальный риск жизненного цикла, не решаемый выбором WPF.
5. Браузер нужен для входа. Проверить Firefox 115 ESR на Win7/Server 2012 с конкретной страницей входа и провайдером; наличие браузера не гарантирует работу OAuth/JavaScript.
6. Системный браузер может быть Internet Explorer или старый Chrome. Показывать возможность скопировать адрес входа/выбрать внешний браузер; токены и device secrets в адрес не включать.
7. Учитывать системный/корпоративный proxy, 407, PAC/auto-detect задержки, антивирусное TLS inspection и firewall. Проверить фактическое поведение выбранного HttpClient handler.
8. Контроль соединения и idle-stream timeout отделить от лимита всей генерации. Не считать паузу между токенами мгновенным сбоем; согласовать разумные defaults с backend maxDuration.

## 13. Локальное хранение и диагностика

- Данные: `%LOCALAPPDATA%\Arnion\ArniLite`; настройки при необходимости в `%APPDATA%\Arnion\ArniLite`. Не использовать `.arni-code`/профиль текущего продукта.
- Схема хранения имеет version; миграции с backup и возможностью обнаружить несовместимую новую версию.
- История содержит user/assistant messages, tool lifecycle, partial status, model ID, workspace identity, timestamps и серверные request IDs, если они доступны.
- Не сохранять токен в истории, crash log, аргументах командной строки или URL. DPAPI связан с текущим Windows-пользователем; перенос папки не переносит авторизацию.
- На диске могут оставаться пользовательские тексты и вывод команд. Дать удаление диалога, очистку данных и явную политику хранения. Не заявлять шифрование истории, если реализован только DPAPI для токена.
- История пользователя на этом ПК не синхронизируется с web chat автоматически. Серверный usage journal не является резервной копией transcript.
- По умолчанию технические логи не включают промпты, содержимое файлов и полный stdout. Диагностический экспорт показывать пользователю перед сохранением/отправкой.
- Предложенная log quota — 20 МиБ с ротацией. Восстановление повреждённой записи не уничтожает весь чат.
- Отдельно отображать «нет сети», «не доверен сертификат», «нужен Framework», «требуется вход», «нет бюджета», «команда недоступна».

## 14. Установка, обновления и сосуществование

- Имена: `ArniLite.exe`, отдельный application ID, ярлыки и registry keys.
- Два артефакта MVP: `ArniLite-win-x64.zip` и совместимый с Win7/2012 user installer. Версию packaging tool тоже проверить на старых ОС.
- Установка приложения без администратора в профиль пользователя; prerequisites — отдельный понятный шаг. Нельзя переписать существующую установку ArniCode.
- Приложение работает на Win11 с установленным Framework 4.8.1 как совместимым in-place runtime; не пытаться downgrade Framework.
- MVP: проверка версии/ссылка на подписанный пакет и ручное обновление; предусмотреть минимальные OS/runtime requirements в метаданных. Полноценное auto-update — P1.
- Для auto-update нужны product=`arni-lite`, architecture, channel, version, minimum OS/Framework, checksum и подпись/проверяемый trust anchor; фиксированная allowlist хостов.
- SHA-256 рядом с пакетом защищает от повреждения, но сам по себе не подтверждает издателя. Проверить подпись и доверие цепочки на Win7; не отключать validation ради старой ОС.
- Не использовать stable feed современного ArniCode: он может поставить несовместимый Electron-продукт поверх Lite.
- Обновление не выполняется посреди локальных действий; история мигрируется с backup, downgrade не повреждает её молча.

## 17. Проверки и критерии приёмки

### 17.1. Автоматические проверки

- SSE: UTF-8 split, JSON split, CRLF/LF, multiline data, keepalive, несколько events/chunk, tools с непоследовательными индексами, EOF без DONE, length, usage-only, error.
- Agent loop: zero/one/multiple tools, denial, malformed args, unknown tool, отмена на каждой стадии, лимиты, повторный ID с другими аргументами, restart/replay.
- Файлы: traversal, prefix collision, UNC/device/ADS, junction/reparse, stale hash, unsaved buffer, read-only файл, disk full, atomic replacement и backup.
- Платформа: manifest/реальная версия ОС, отсутствующий новый Win32 API, DPI/RDP/software rendering, long paths и второй экземпляр приложения.
- Процессы: stdout+stderr flood, long line, кириллица, quoting/metacharacters, nonzero exit, PowerShell error, stdin request, timeout, дети/внуки, cancellation/closing app.
- Storage: усечённый journal, неверная schema, миграция и отказ downgrade, token redaction, DPAPI failure после переноса профиля.
- API: строковые/объектные errors, invalid token, missing capability, бюджет, retries, отмена и поздний settlement, context limit.
- Auth: TTL, denial, polling throttling, неверный challenge, повторное consume, потерянный ответ, отсутствие client secret в binaries/config/logs.

Тесты должны проверять поведение и опасные границы, а не копировать реализацию. Сетевые mocks не заменяют реальный старый Windows-runtime.

### 17.2. Обязательный end-to-end на каждой основной ОС

1. Установить/распаковать доставляемый пакет под обычным пользователем.
2. Открыть отзывчивый UI, пройти диагностику и настоящий browser login.
3. Получить аккаунт и доступные модели; выполнить реальный streaming chat на тестовом аккаунте.
4. В проекте с кириллицей и пробелами прочитать текстовый файл, предложить изменение и показать diff.
5. Отменить изменение: файл не изменился. Затем одобрить: корректные encoding/line endings и backup.
6. Модель вызывает `run_command`, клиент показывает команду/cwd, выполняет её и возвращает настоящий результат; модель отвечает по результату.
7. Запустить fixture с дочерним процессом; «Стоп» действительно убирает принадлежащее приложению дерево в поддерживаемом сценарии.
8. Оборвать сеть во время inference: partial state сохранено, команда не повторяется сама.
9. Закрыть/аварийно завершить приложение около side effect; восстановление показывает outcome_unknown без повторного запуска.
10. Проверить запрос за пределы проекта через file tool: отказ; отдельно подтвердить, что UI честно описывает shell scope.
11. Проверить 401/402/429/503, отсутствие сети и ошибку TLS без обхода сертификатов.
12. Перезапустить, восстановить историю, сверить usage по chatId и серверный бюджет.
13. На Win10/11 проверить тот же x64-пакет и сосуществование с текущим ArniCode.
14. На Server 2012 повторить в RDP; на Win7 — в обычном сеансе и под контролируемым launcher/job fixture.

Сценарии используют отдельный тестовый проект и аккаунт с ограниченным бюджетом. Не выполнять команды над реальными пользовательскими файлами ради проверки.

### 17.3. Definition of Done для MVP

- Все обязательные функции раздела 3.1 реализованы либо изменение scope явно согласовано и записано.
- Есть повторяемые build instructions, locked dependencies и release manifests.
- Матрица ОС заполнена доказательствами: версия образа/обновления, hash пакета, результат и ограничения.
- Есть реальный tool-call round trip с live backend; отдельно проверены отмена, billing errors и local side effects.
- Нет автоматического replay неизвестной команды, нет зависимости от modern Node/WebView2 и нет подмены TLS validation.
- История восстанавливается после падения, токены не попадают в экспорт/логи.
- Выпущенные пакеты устанавливаются под обычным пользователем, не повреждают ArniCode и не используют его update feed.
- Опубликован честный список ограничений и измерения производительности.

Успешная компиляция, запуск окна на Windows 11 или mock test не доказывают готовность для Windows 7/Server 2012.

## 18. Этапы, точки принятия решения и оценка

### G0. Проверочный прототип: ориентировочно 3–5 рабочих дней

Выдать один net48 executable с минимальным WPF UI/AvalonEdit; доказать запуск на Win7 SP1, Server 2012 и Win11, TLS к API на настоящем Schannel, streaming текста, открытие страниц входа Yandex и Google в браузере старой ОС, запуск PowerShell выбранным способом под антивирусом и управление деревом простой команды. Снять первые memory/startup measurements. Зафиксировать dependency versions и auth ADR. Параллельно с G0 на backend делается мост входа из 8.3 (оценка 1–2 рабочих дня, не проверена).

Нельзя начинать масштабный UI/агентный перенос до проверки TLS, login и process cancellation на старой ОС. Если старые образы/VM недоступны, продолжать независимую работу, но статус compatibility оставить «не проверено» и явно указать недостающую проверку.

### G1. Рабочий агент и данные: ориентировочно 1–2 недели

Реализовать корректный SSE/tool assembler, оркестратор, read/search/change/command tools, разрешения, journal/recovery, историю и budget UI. Пройти fixtures и live tool round trip.

### G2. Упаковка и испытания: ориентировочно 1–2 недели

Закончить installer/portable, подпись, диагностику, quoting/encoding, proxy/RDP/Job Object cases, performance и user acceptance на матрице.

Порядок общей оценки — **3–5 рабочих недель для одного разработчика при доступных VM и backend**. После ревью 1.1 эта оценка относится к объёму без Markdown-рендерера и без OAuth в клиенте; мост входа на backend считается отдельно. Ревью считает полный DoD раздела 17 на четырёх ОС ближе к 6–10 неделям: код пишется быстро, время уходит на ручную матрицу испытаний, установщик и подпись. Обе цифры — оценки, не измерения.

Если нужно уложиться в 3–4 недели, сокращать в таком порядке и каждое сокращение записывать как изменение scope:

1. Первая поставка — только portable ZIP; user installer следом.
2. Обязательная матрица первой поставки — Win7 SP1 и Win11; Server 2012 и Win10 проверяются сразу после, статус до проверки — «не проверено».
3. Встроенный редактор сводится к просмотру файла и diff; правка текста вручную — следом.
4. Журнал из 9.4 остаётся (запрет автоматического повтора side effect не сокращается), но восстановление незавершённого turn упрощается до показа `outcome_unknown`.

Не сокращать: проверку TLS и сертификатов, согласие на команды и запись, остановку процессов с честным описанием ограничений, хранение токена через DPAPI. Интерактивный терминал, неподготовленные старые ОС или P1-функции увеличивают срок.

## 19. Альтернативы и условия пересмотра

| Вариант | Когда выбрать | Проблема |
| --- | --- | --- |
| WPF/net48 + AvalonEdit | Нужен Windows-продукт без браузерного runtime, основа этого документа | Новый C# UI и собственный небольшой agent loop |
| Avalonia + AvaloniaEdit, `net48` на Windows и современный .NET на Linux | Linux-клиент становится обязательным до начала работ над UI | Работа Avalonia на Win7 SP1 не проверена; Linux добавляет свой ProcessRunner, хранилище токена, упаковку и матрицу — по оценке ревью +2–3 недели |
| Маленькая оболочка Electron 22 | Самый быстрый JS/TS proof of concept и перенос web UI | Устаревшие Chromium/Node, pinning старых пакетов; это отдельный клиент, не downgrade VS Code |
| Lite XL + наш плагин | Именно готовый лёгкий редактор — основной продукт | Lua/C UI и интеграция; сначала проверить релиз на Win7 SP1 и требования обновлений |
| Firefox + локальный helper | Допустим браузерный интерфейс, хочется использовать web chat | Новый authenticated browser↔helper протокол, origin/CORS/loopback риски и жизненный цикл helper |
| Старый VS Code fork | Нужны конкретные функции старой IDE и есть ресурс на перенос | Современный агент/API не появятся автоматически; долгосрочный fork |

Для Lite XL документация заявляет Windows 7 с неоднозначной пометкой «Service Pack 2». Не превращать это в гарантию для пользовательского Win7 SP1 без запуска.

Tauri/WebView2 не считать автоматическим решением legacy: WebView2 на Win7 ограничен старой веткой 109. Перенос с Electron на другую web-оболочку не обязательно устраняет проблему браузерного движка.

## 20. Поручение следующему агенту и вопросы для ревью

Перед реализацией выполнить независимое техническое ревью документа и перечислить ошибки/недостающие решения. Особое внимание:

1. Есть ли более простая основа, сохраняющая реальные Win7 SP1 и Server 2012, хороший чат и обычные команды?
2. Установимы ли выбранные Framework/AvalonEdit зависимости на исходные системы пользователя?
3. Проходят ли TLS и внешний login без ослабления проверки сертификатов?
4. Решено в 1.1: вход через мост поверх существующего веб-входа (8.3). Проверить, что мост не позволяет привязать чужой аккаунт (подмена `request_id`, фишинговая ссылка, повторное использование) и что оба провайдера проходят в браузере старой ОС.
5. Как гарантируется отсутствие повторного side effect при network failure/crash?
6. Как устроена остановка дерева на Win7 при внешнем Job Object? Где приложение честно отказывается от команд?
7. Достаточен ли неинтерактивный ProcessRunner для пользовательских задач? Если нужен TUI, пересчитать scope и срок.
8. Не обещает ли UI sandbox, которой нет? Сохраняются ли file preview, scope и permission semantics?
9. Поддерживает ли реальный backend/model выбранный tools protocol и корректное списание после отмены?
10. Какие испытания доказали «быстрее» и совместимость одной сборки на всех целевых ОС?

Результат первого этапа: краткий review, ADR по UI/auth/process runner, список блокирующих проблем, runnable G0-артефакт с инструкцией и таблица фактически пройденных проверок. Не выдавать предполагаемую совместимость за испытанную и не расширять MVP до полного VS Code.
